# Seed data

Run these after the migrations, in numeric order.

| File | What it is | Rows |
| --- | --- | --- |
| `001_districts.sql` | Every district of Bangladesh, Bangla and English, with centroid | 64 |
| `002_upazilas.sql` | Every upazila, Bangla and English, with centroid | 494 |
| `003_hospitals.sql` | Starter hospital list for five cities | 42 |
| `004_admin_settings.sql` | Default settings, including the email master switch | 10 |

All four are safe to run more than once.

## Where the geography came from

`001` and `002` are generated, not typed. Regenerate them with:

```bash
node scripts/build-geo-seed.mjs
```

Names come from [ifahimreza/bangladesh-geojson](https://github.com/ifahimreza/bangladesh-geojson).
Every upazila centroid is computed from that upazila's own boundary polygon
rather than looked up, so each coordinate traces back to a shape you can
inspect.

**494, not 495.** The published open data has 494 upazilas. Bangladesh is
usually said to have 495, and new upazilas do get created. If you know which
one is missing, adding it is a one line pull request.

**Ten upazilas have a NULL centroid.** They have no usable boundary polygon in
the source. The app falls back to the district centroid for those, which is
honest about its own precision rather than pretending. Filling one in is also a
one line pull request.

### The trap in this data, so nobody falls into it twice

There are several published Bangladesh geocode datasets and **they do not share
an id space.** Upazila id 283 is Abhaynagar in one and Dakshinsurma in another;
district id 46 is Feni in one and Manikganj in another.

An earlier version of the generator joined two of them on those ids. Nothing
crashed, the SQL looked perfect, and Debidwar in Cumilla was given a centroid
150km away in Barishal. That is why the generator now:

- takes all three inputs from a single repository, and
- rejects any upazila centroid more than 120km from its own district centre.

The distance check is the important part. If you point this script at a
different source, keep it.

## Hospitals

`003_hospitals.sql` is generated by:

```bash
node scripts/build-hospital-seed.mjs
```

The names are curated by hand. The coordinates are looked up from Nominatim and
checked against the district centre, because a hospital pin that is confidently
wrong is worse than no pin at all when someone is trying to get there.

**The committed file has no coordinates.** It was generated in an environment
with no route to Nominatim, so every position is NULL. Hospitals still appear
in the dropdowns and the map falls back to the district. Run the script on a
machine with normal internet access and commit the result to fill them in — it
takes about a minute, since it waits a second between lookups as OSM's usage
policy asks.
